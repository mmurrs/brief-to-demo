# Demo Contract

Use this template to turn source material into a bounded product and build decision. Keep the completed contract to roughly one page.

## 1. Source-backed mandate

**Outcome:** What change does the source explicitly seek?

**Required capabilities:** Which two to five requirements are essential to that outcome?

**Constraints:** Which rules, existing responsibilities, technology boundaries, time limits, or exclusions must remain true?

## 2. Primary user and job

**Primary user:** Choose the user whose end-to-end workflow will be demonstrated.

**Trigger:** What causes the user to begin?

**Job:** What must the user accomplish?

**Current pain:** Where does the current workflow cost time, create confusion, introduce risk, or require avoidable coordination?

Choose one primary user even when the system serves several. Include a second role only when the value cannot be demonstrated without a handoff.

## 3. Solution thesis

Complete this sentence:

> For **[primary user]**, the product enables **[capability]**, which improves **[source-supported outcome]** while preserving **[important constraint]**.

This is a candidate explanation of how to fulfill the mandate, not a new mandate.

## 4. Prototype hypothesis

Complete this sentence:

> If the audience can see **[user]** move from **[trigger]** to **[meaningful outcome]** through **[core mechanism]**, the demo will make **[most important claim]** believable.

## 5. Golden path

Write five to seven observable steps:

1. The user starts with...
2. The user identifies or selects...
3. The system reveals or requires...
4. The user completes...
5. The system routes, calculates, or records...
6. A second role responds... *(only when essential)*
7. The workflow ends with...

Each step should change the state, reduce uncertainty, or demonstrate value. Remove navigation that proves nothing.

## 7. Boundaries

**Included:** The exact roles, use case, data, and outcome demonstrated.

**Excluded:** Adjacent workflows or production capabilities intentionally left out.

**Simulated:** External systems, automation, or data represented with fixtures or mocks.

**Assumptions:** Unverified beliefs that influenced the prototype.

**Unknowns:** Questions that could change the real solution but do not block this demonstration.

## 8. Success signal

Choose one outcome signal tied to the mandate. Add one diagnostic only if it helps explain why the outcome changed.

- **Outcome:** What should become faster, easier, safer, clearer, or more reliable?
- **Diagnostic, optional:** What operational behavior explains movement in the outcome?

Avoid vanity counts that rise merely because the interface exists.

## Contract quality check

- Every claimed problem or requirement is source-backed or clearly labeled.
- One golden path carries the main argument.
- The final state is more meaningful than “form submitted.”
- Each major build element has a proof purpose.
- Exclusions make the scope believable within the timebox.
- The success signal measures the desired outcome, not just feature usage.
